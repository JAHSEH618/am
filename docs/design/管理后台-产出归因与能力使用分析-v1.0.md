## 二、归因分析 `/attribution`

### 2.1 业务问题

回答管理者：**团队的代码产出有多少归功于 AI？归到哪个工具（Cursor/Claude Code/Codex…）、哪个模型、哪个人、哪个项目？**

### 2.2 归因口径：双档分层

- **B 档「确定 AI 产出」**：`git_commit.message_body` 命中 AI trailer——`Co-Authored-By: Claude` / `Generated with [Claude Code]` / Codex、Cursor 等各工具签名（匹配规则表在实现时穷举为常量 + sys_config 可扩）。语义：**AI agent 亲自产出/参与了该 commit**。误报≈0。
- **A 档「疑似 AI 辅助」**：commit 落在同 `user_code`、repo 归一化相等的 AI 会话活动窗口 **±30 分钟** 内（沿用现网 `AiPenetrationService` 的既有公式）。语义：**该 commit 完成时段内此人正与 AI 协作于同一仓库**。是上限口径——重度用户几乎所有 commit 都会命中，**读数时不得把 A 档当结论**，前端必须 B/A 分列展示并配口径释义。

B ⊆ A 在绝大多数情况下成立（agent 提交时会话必然活跃）。展示上 B/A 互斥统计：命中 B 的不再重复计入 A。

### 2.3 与现网机制的关系（重要）

- 历史上 `git_commit` 曾有预计算列 `ai_assisted` / `ai_assist_confidence` / `ai_session_ids`，已被 `GitCommitSchemaPatches` 下线，推断改为**查询时 JOIN**（`GitCommitRepository.aiPenetrationLines`：同人 + repo 归一 + ±30min）。
- 本方案等于**把查询时推断升级回预计算**，但与旧列的区别：旧列是 ingest 时写死、身份归因修正（v1.0.2 文档）之前误差大且无法重算；新表**独立于 `git_commit`、由任务全量/增量重算**，口径变更可整表重建，不污染事实表。
- **`AiPenetrationService` 迁移到读 `git_commit_attribution`**：北极星渗透率的口径从「查询时 A 档推断」变为「预计算 A∪B 档」，数值近似不变（B⊆A），性能从全窗口 JOIN 变为单表聚合。Dashboard 语义不变，释义文案同步更新。
- 身份正确性（commit → `user_code`）是本方案的**前置依赖**，契约见《员工AI产出-Git采集与归因方案-v1.0》§三；本文不重复其内容。

### 2.4 归属规则（单一归属）

一个 commit 的窗口可能与多个会话（多工具/多模型）重叠。规则：

1. **B 档优先直接映射**：trailer 文本可识别工具时（如 `Generated with Claude Code`），`target_type` 直接取 trailer；再在窗口内找该工具的会话确定 `session_id`/`model`，找不到则 session 置空、model 记 `unknown`。
2. **A 档单一归属**：取「commit_time 之前最近一次有活动事件（`ai_session_event`）」的会话；并列时取窗口重叠时长最长者。该会话的 `target_type`/`model` 拿走全部计数。
3. 归因行必须带 `session_id`，前端 commit 明细可跳转 `/sessions/:id` 人工核查。
4. **各维度求和 = 总数**（单一归属保证交叉透视可加和）。

### 2.5 指标口径

- **AI commit 数**（默认指标，B/A 分列）
- **AI 净行数**：`lines_added`（展示辅以 `lines_deleted`）
- **AI 占比**：AI commit ÷ 全部 commit（或行数口径），分子分母**均排除 merge commit**（`is_merge=1` 全口径不参与归因与统计）

### 2.6 数据模型

```sql
CREATE TABLE IF NOT EXISTS git_commit_attribution (
    id               BIGINT      NOT NULL,              -- @TableGenerator，接 id_sequences
    commit_id        BIGINT      NOT NULL,              -- -> git_commit.id
    repo_url         VARCHAR(512) NOT NULL,             -- 冗余，避免透视 JOIN
    user_code        VARCHAR(64) NOT NULL,
    project_name     VARCHAR(128) DEFAULT NULL,
    commit_time      DATETIME    NOT NULL,
    lines_added      INT         NOT NULL DEFAULT 0,
    lines_deleted    INT         NOT NULL DEFAULT 0,
    tier             VARCHAR(8)  NOT NULL,              -- 'B' 确定 / 'A' 疑似 / 'NONE' 未命中
    trailer_kind     VARCHAR(32) DEFAULT NULL,          -- B 档命中的 trailer 类型
    session_id       BIGINT      DEFAULT NULL,          -- 归属会话（B 档可空）
    target_type      VARCHAR(32) DEFAULT NULL,          -- 归属工具
    model            VARCHAR(128) DEFAULT NULL,         -- 归属模型
    overlap_seconds  INT         DEFAULT NULL,          -- A 档窗口重叠秒数（核查用）
    backfilled       TINYINT     NOT NULL DEFAULT 0,    -- 1=上线前历史回溯所得
    computed_time    DATETIME    NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_commit (commit_id),
    KEY idx_user_time (user_code, commit_time),
    KEY idx_tier_time (tier, commit_time),
    KEY idx_target_time (target_type, commit_time)
) COMMENT 'commit→AI 产出归因（每 commit 一行，含未命中行，便于占比分母）';
```

- **每个非 merge commit 一行**（含 `tier=NONE`），占比分母直接来自本表，无需回 `git_commit`。
- 建表走 `schema.sql` + 存量库 `*SchemaPatches`（遵循仓库惯例，`ddl-auto=none`）。

### 2.7 计算与回溯

- **增量**：commit ingest 成功后（`GitCommitIngestService`）投递归因计算；会话仍在进行导致的窗口右缘未闭合，由夜间批补算兜底。
- **夜间批**：每日重算近 N 天（默认 2 天）窗口，修正迟到会话/迟到 commit。
- **全量回溯**：一次性任务扫全部历史 commit，`backfilled=1`。B 档回溯（trailer 文本匹配）可信；A 档回溯依赖历史会话事件完整性，前端趋势图对回溯区间注明「上线前数据为回溯推算」。
- **口径版本**：trailer 规则或窗口参数变更时整表重建（表是纯派生物，可随时 drop 重算）。

### 2.8 页面（`/attribution`）

1. **顶部**：团队级 AI 产出占比趋势（B/A 双档堆叠 + 占比线），窗口切换沿用现有 RangePicker 惯例。
2. **交叉透视区**：行/列维度可选（人、项目、工具、模型），指标可切（commit 数/净行数/占比），可组合筛选；单元格点开 → commit 明细抽屉（subject、行数、档位、归属会话跳转链接）。
3. 所有查询只打 `git_commit_attribution` 聚合，受 §五性能指标约束。

## 三、能力使用分析 `/capability`（一页两 tab）

两 tab 共享骨架：**排行（调用次数/使用人数/会话数）+ 趋势图 + 人×维度覆盖矩阵 + 按人下钻**。查询层复用/扩展 `SlashCommandStatSupport` 与 `AiSessionMessageRepository.loadSlashHitsJsonOnlyInWindowGlobal` 系列；前端照 `Tools.tsx` / `TeamOverview.tsx` 的「Slash Commands 分布」模式建页。

### 3.1 Skill tab

- **数据源已通**：`ai_session_message.slash_skill_count` / `slash_hits_json`（`kind=skill` 显式、`kind=nl_skill` NL 隐式，identification 由 `UserSlashInvocationExtractor` + `NlSkillAttributionSupport` 在 ingest 时完成）。
- 排行与趋势按 skill 名聚合，**显式/NL 隐式分档展示**（沿用现网命令蓝/技能紫的双色惯例，NL 档另加区分）。
- **人×skill 覆盖矩阵**：行=员工、列=数据中出现过的 skill（按使用量排序，TopN 外折叠）、格=窗口内调用次数。**纯数据驱动，不建名录**——零使用的推广技能不可见是已接受的取舍；矩阵回答「实际在用什么」。
- 已知噪音：NL 隐式识别是启发式（Read SKILL.md + 落地工具），矩阵页配口径释义（沿用 `Analysis/constants.ts` 指标释义模式）。

### 3.2 插件（MCP）tab

**插件定义 =**

1. **MCP server**：从 `ai_session_event.tool_name`（TOOL_CALL 事件，已有 `idx_tool_name`）与 `content_parts_json` 的 `tool_call.tool_name` 解析 `mcp__<server>__<tool>` 前缀（大小写不敏感——agent 端 `NormalizeToolName` 会首字母大写为 `Mcp__...`），得到 **server × tool 两级维度**。
2. **插件市场命名空间技能**：`slash_hits_json` 中 token 形如 `<namespace>:<skill>`（如 `superpowers:brainstorming`）者，归入插件维度（namespace = 插件名）。

- 页面：server 级排行（可展开 tool 级明细）+ 命名空间技能排行；趋势；人×server 矩阵；按人下钻。
- **纯服务端解析、历史全量可回溯（数据已在库）、不改 agent 不发版**；「装了没用」的安装态采集**明确排除**本期。

### 3.3 预聚合（性能前置）

`slash_hits_json` / `tool_name` 的窗口扫描在 30 天窗口下无法满足 §五指标，能力页**不做实时扫表**：

- 新增日聚合表 `capability_daily`（`work_date` × `user_code` × `kind`(skill/nl_skill/mcp/plugin_ns) × `item`(skill 名/server/tool/namespace) → `invoke_count` / `session_count`），由 `DailySummaryAggregator` 同节奏的任务维护（当日 ensureFresh + 历史定型），一次性回溯任务补历史。
- 排行/趋势/矩阵全部查 `capability_daily`；「使用人数/会话数」按日聚合行去重计算。

## 五、控制台加载性能治理（同版本交付）

### 5.1 验收指标（性能预算）

| 指标 | 目标 |
| --- | --- |
| 首屏可交互（局域网，冷缓存） | ≤ 2s |
| 所有页面数据接口 P95（30 天窗口） | ≤ 3s |
| 前端 15s 超时（`client.ts:41`） | **任何接口不得触发**；重导出类接口显式放宽并加进度反馈 |
| 新页面（`/attribution`、`/capability`） | 按同一标准设计，上线即达标 |

### 5.2 现状盘点（已核实）

- **构建侧健康**：路由级懒加载齐全；`manualChunks` 已拆 antd(1.3M)/echarts(1.0M)/pdfmake(1.3M)/xlsx(276K)；HTTP 压缩开启；assets 365d immutable、index no-cache。首屏下载路径常规优化已到位。
- **超时根因在接口层**：axios 全局 15s，audit 接口已被迫特判 120s；`ProjectsWindowSnapshotCache` 的存在证明窗口聚合曾是慢点。嫌疑名单：`/analysis`（扫 `slash_hits_json`）、`/dashboard`（`aiPenetrationLines` 全窗口 JOIN——本方案 §2.3 顺带消灭）、`/sessions` 列表。

### 5.3 治理手段

1. **测量先行**：为 admin 接口加耗时日志/慢查询清单（阈值 1s），拿到真实 Top 慢接口，不凭体感修。
2. **预聚合推广**：慢接口按「预聚合表（`daily_summary`/`capability_daily`/`git_commit_attribution`）+ 快照缓存（`ProjectsWindowSnapshotCache` 模式）」二选一改造；查询时大 JOIN 一律下线。
3. **前端**：重接口加载态/骨架屏；导出类（pdf/xlsx）保持独立 chunk 按需加载。
4. **验收**：上线前用 30 天窗口 + 生产量级数据实测全页面，出对照表附在 PR。
5. 部署侧（nginx 静态缓存、HTTP/2、首屏 preload antd/echarts）**后续可选**，不阻塞本版本。

1. `/attribution`：任一维度组合求和 = 总数（单一归属不变式）；B/A 分列且口径释义可见；merge commit 不出现在任何数字里；commit 明细可跳转归属会话；回溯区间有标注。
